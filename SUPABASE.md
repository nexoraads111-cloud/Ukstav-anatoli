# Supabase — налаштування та безпека

Проєкт у Supabase зберігає **заявки**, **відгуки**, **фото** і **логін адміна**.
Поточний проєкт: `gqcogdqqgxzuteaoaxza` (регіон EU West). Ключ у `js/supabase-config.js` — публічний (anon/publishable), це нормально.

> Ніколи не кладіть у репозиторій або в браузерний код `service_role`-ключ, токени Telegram/WhatsApp, паролі.

## Налаштувати з нуля (новий проєкт)

1. supabase.com → **New project** (регіон EU).
2. **Authentication → Users → Add user** — e-mail + довгий унікальний пароль. Це логін в `admin.html`.
3. **SQL Editor** → вставити весь `supabase/setup.sql` → **Run**.
   * E-mail адміна в SQL (`ukstav.sk@gmail.com`) має збігатися з користувачем із кроку 2 — інакше змініть його в SQL до запуску.
   * Скрипт можна запускати повторно: дані й завантажені фото він не стирає.
3b. **SQL Editor** → вставити весь `supabase/seed-gallery.sql` → **Run** — заносить у базу 134 початкові фото галереї, щоб їх можна було редагувати в адмінці. Запускається лише якщо в галереї ще немає жодного фото (повторний запуск нічого не дублює).
4. **Project Settings → API** → скопіювати *Project URL* і *anon/publishable key* у `js/supabase-config.js`.

## Обов'язково в панелі Supabase (SQL це зробити не може)

* **Authentication → Sign In / Providers → Email** → вимкнути *Allow new users to sign up*. Права адміна й так лише в одного акаунта, але відкрита реєстрація — зайва поверхня.
* **Authentication → Policies / Password** → увімкнути *Leaked password protection* (якщо доступно в плані).
* **Authentication → Multi-Factor** → TOTP — **поки не вмикайте**: сторінка `admin.html` ще не вміє запитувати код, і ви не зможете увійти. Спершу потрібно додати цей крок у `js/admin.js`.
* Пароль адміна — унікальний, ніде більше не використовується.

## Хто що може (перевірено тестами по ролях)

| Роль | Фото | Заявки | Відгуки | Storage |
|------|------|--------|---------|---------|
| Відвідувач (anon) | лише читати | лише створити (прапорці доставки виставити не може) | створити (на модерації) + читати схвалені | лише публічні посилання |
| Чужий зареєстрований акаунт | лише читати | нічого | лише схвалені | нічого |
| Адмін (`admin_users`) | читати/додавати/міняти/видаляти | читати, змінювати статус і примітку, видаляти | схвалювати, видаляти | вантажити/видаляти |

Додатково: ліміт частоти (3 заявки з одного номера на годину, 10 відгуків на годину), адмін не може змінити контактні дані клієнта в заявці.

## Таблиця `site_images`

Одна таблиця для всіх фото: `slot` (hero, hero-light, …), `category` (`gallery` — фото галереї), `storage_path` (шлях `images/…` у репозиторії або файл у bucket `site-images`), `alt_text`, `sort_order`, `work_types text[]`, `project_id`, `is_visible` (сховане фото не показується на сайті).
Публічно читається все, змінює лише адмін.

## Додати ще одного адміна

SQL Editor:
```sql
insert into public.admin_users (user_id)
select id from auth.users where email = 'nova.osoba@example.com';
```

## Заявки на WhatsApp автоматично

Як це працює: клієнт надсилає форму → заявка зберігається в таблиці `leads` → тригер `leads_notify` викликає Edge Function `notify-lead` → вона шле повідомлення на **+421 950 405 659** через офіційний WhatsApp Cloud API (Meta). Клієнту нічого натискати не треба. Якщо відправка не вдалась — заявка однаково збережена, а в адмінці (*Dopyty*) біля неї буде попередження з причиною.

Функція вже розгорнута, у базі все налаштовано. **Не вистачає лише ключів Meta** — їх можна покласти тільки в секрети Supabase (ніколи в код чи чат).

1. [Meta for Developers](https://developers.facebook.com/) → створити застосунок (тип *Business*) → додати продукт **WhatsApp**. Там же — *API Setup*: **Phone number ID** (ідентифікатор номера-відправника).
2. Номер-відправник: Meta дає безкоштовний тестовий номер для перевірки (отримувачів треба додати й підтвердити кодом — туди додайте +421 950 405 659). Для постійної роботи підключіть власний номер фірми, який **не** використовується в звичайному застосунку WhatsApp (інакше його треба спершу відв'язати) — відправником не може бути той самий номер, що отримує.
3. Постійний токен (тимчасовий з *API Setup* живе 24 години): *Business Settings → System users* → створити системного користувача → *Generate token* з правом `whatsapp_business_messaging`.
4. Шаблон повідомлення (потрібен, бо ви пишете першими, а не у відповідь клієнту): *WhatsApp Manager → Message templates* → категорія **Utility**, мова **Slovak (sk)**, назва `new_lead`, текст із трьома змінними:
   `Nový dopyt z ukstav.sk. Meno: {{1}}, telefón: {{2}}, popis: {{3}}. Ozvite sa klientovi čo najskôr.`
   (змінна не повинна стояти на самому початку чи кінці тексту; Meta схвалює шаблон зазвичай за кілька хвилин).
5. Supabase → **Edge Functions → Secrets** → додати:

   | Секрет | Значення |
   |--------|----------|
   | `WHATSAPP_TOKEN` | токен із кроку 3 |
   | `WHATSAPP_PHONE_NUMBER_ID` | Phone number ID з кроку 1 |
   | `WHATSAPP_TEMPLATE` | `new_lead` |
   | `WHATSAPP_TEMPLATE_LANG` | `sk` (або код мови шаблону, напр. `en_US`) |
   | `WHATSAPP_TO` | необов'язково; за замовчуванням `421950405659` |

6. Перевірка: надішліть заявку з сайту. На WhatsApp прийде повідомлення, а в адмінці біля заявки з'явиться «✓ Odoslané na WhatsApp». Якщо ні — там же буде текст помилки від Meta (напр. шаблон ще не схвалений, отримувач не доданий, токен прострочений).

Захист: токени лише в секретах функції; функція приймає тільки id заявки, читає її з бази сама, не відправить одну заявку двічі й не більше 20 повідомлень на годину (форма має власні ліміти). Дивіться `supabase/functions/notify-lead/` (тести відправника: `node --experimental-strip-types --test supabase/functions/notify-lead/senders.test.ts`).

**Telegram (додатково, необов'язково):** ті ж секрети `TELEGRAM_BOT_TOKEN` і `TELEGRAM_CHAT_ID` — функція надсилатиме й туди.
Якщо колись у git потрапляли старі токени Telegram/WhatsApp (Meta) — їх треба **перевипустити** (BotFather / Meta), видалення з коду їх не знешкоджує.
